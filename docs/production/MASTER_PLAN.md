# Human Enough! 리마스터 마스터 플랜

목표: 컨셉 아트(`submission-cover.png`, `festival.png`, `cast.png`) 수준의 화면을 실제 게임에서 구현해 출시하고, 포트폴리오 케이스 스터디로 정리한다. 게임 규칙, 멀티플레이 서버, 테스트는 유지한다. 바꾸는 것은 보이는 것과 들리는 것이다.

## 1. 진단(2026-11-08 기준, `baseline/` 참조)
| 영역 | 현재 | 왜 아마추어처럼 보이는가 |
|---|---|---|
| 조명·분위기 | "Fireworks night"인데 화면은 낮처럼 밝은 초록 | 키아트의 핵심인 등불과 밤의 대비가 없다 |
| 캐릭터 | Blender 스크립트로 조립한 23개 모델. 캐릭터당 50~186k 삼각형, 50~110개 파츠, 9~17개 강체 뼈, 애니메이션 클립 0개(코드로 흔듦), 512px 텍스처 1장 | 무겁기만 하고 디테일은 낮다. 팔꿈치·무릎이 없어 인형처럼 움직이고, 재질이 단색이라 장난감 같다 |
| 인간 변장·NPC | 같은 몸에 머리색만 다르다 | 7명 변장과 9명 손님을 구분할 수 없다 |
| 환경 | 상자형 노점, 단순한 등불, 평평한 돌길 | 손맛과 밀도가 없다 |
| UI | 흰 반투명 웹 카드 | 게임 세계와 따로 논다 |
| 코드 구조 | 51 KB `game.js`에 렌더·조명·오디오·후처리가 섞여 있다 | 여러 채팅이 동시에 작업하면 충돌한다 |

검사기 결과: 현재 런타임 모델 23개 전부 ASSET_CONTRACT v1 FAIL(`baseline/validator-v0.txt`).

## 2. 제작 방식
- 컨셉 이미지 → 깨끗한 A-pose 턴어라운드(생성 이미지) → 이미지→3D(Higgsfield: Tripo H3.1 multiview · Meshy 7 · Hunyuan3D v3) → Blender 헤드리스(pip `bpy` 5.2) 정리·UV·베이크·리그 → 계약된 클립 → glTF(meshopt + KTX2) → `rig-v2`가 AnimationMixer로 재생.
- 실제 스튜디오의 순서를 따른다: **기반 → 대표 1개(미즈) 승인 → 같은 방법으로 양산 → 연출과 사운드 → 최적화 → 출시.**
- 모든 방은 `ASSET_CONTRACT.md` 규격을 지키고 `tools/validate-glb.mjs` PASS를 받아야 병합된다.

## 3. 채팅방 구성(7개 + 본부)
계획을 만든 채팅이 본부(R00)를 맡는다. 새 채팅은 7개이고, 방 하나가 브리프 여러 개를 순서대로 수행한다. 브리프 16개(`briefs/r00~r15.md`)는 그대로 작업 단위로 남는다.

| 방 | 이름 | 수행 브리프 | 시작 | 크레딧(추정) |
|---|---|---|---|---|
| 본부 | PD 겸 아트 디렉터 | R00 | 계획 채팅 | 0 |
| A | 기반 공사 | R01 | 지금 바로(혼자 먼저) | 0 |
| B | 월드 룩: 밤 조명 + 환경(블렌더 우선) | R02 → R04 | A 병합 후 | 50~140 |
| C | 캐릭터 1: 미즈 파일럿 → 폰·콘 | R03 → R06 | A 병합 후 + 크레딧 충전 | 240~360 |
| **게이트 A** | 미즈 승인 + 밤 룩 승인 → 아트 바이블 v1 확정 | | | |
| D | 캐릭터 2: 스미·네무·아카리·카사 | R07 → R08 | 게이트 A 후 | 320~480 |
| E | 인간 캐스트 + 데몬킹 | R09 → R11 | 게이트 A 후 | 400~820 |
| F | UI · VFX · 사운드 | R05 → R10 → R13 | A 병합 후 | 70~190 |
| G | 마감: 미니게임 · 성능 · 출시 | R12 → R14 → R15 | 캐릭터 대부분 병합 후 | 40~120 |

크레딧 합계 추정: **약 1,100~2,100**. 환경은 블렌더 스크립트로 직접 모델링하고, 생성 3D는 유기적인 형태(캐릭터, 나무, 바위)에만 쓴다. C방이 캐릭터 1명의 실제 비용을 측정하면 본부가 다시 계산한다.

## 4. 동시 작업 규칙
- 동시에 열어 두는 작업 방은 **최대 4개**(본부 제외). 순서: A 단독 → B·C·F → (게이트 A) C·D·E·F → G.
- 브리프마다 브랜치 `remaster/rNN-<slug>`와 PR을 따로 만든다. 병합은 본부만 한다.
- 파일 소유권은 각 브리프의 "소유 파일"이 정한다. `game.js`는 R01 이후 본부만 수정한다.
- 방 사이의 소통은 `HANDOFF.md`와 PR 설명으로 한다. 사용자는 "[RNN 완료]" 한 줄 보고를 본부 채팅에 옮겨 붙인다.
- 대화가 길어지면 같은 프롬프트로 새 채팅을 열고 "이어하기"를 덧붙인다. 방 개수는 늘지 않는다.

## 5. 품질 기준(“전문가 수준”의 구체적인 정의)
1. 같은 구도에서 키아트와 게임 화면을 나란히 놓았을 때 색 온도, 명암 비율, 실루엣, 재질이 같은 게임으로 보인다.
2. 게임 카메라 거리에서 7명의 요괴를 실루엣만으로 구분할 수 있다.
3. 캐릭터 동작에 예비 동작, 무게, 성격이 있고 미끄러지는 발이 없다.
4. 모든 주요 행동(포션, 홀리기, 결계, 리빌, 배달, 보스)에 시각·청각 피드백이 있다.
5. 중급 노트북 60 fps, 중급 휴대폰 30 fps, 첫 화면 5초 이내.
6. 모든 에셋의 출처와 라이선스가 기록되어 있다.

## 6. 사용자 결정이 필요한 것
- Higgsfield 크레딧 충전(현재 17.92). Phase 1(A·B·C·F)에는 약 500이면 충분하다. 나머지는 미즈 실측 후 충전한다.
- 출시 채널과 호스팅 비용(R15에서 비교표 제공): itch.io 웹 + 유료 서버 vs Steam.
- 스미의 머리 개수(컨셉 시트 정면은 하나, 측면·후면과 현재 모델은 둘).
- 저장소 공개 여부: GitHub에 현재 public으로 표시된다. 출시 전에 소스·아트를 공개 상태로 둘지 정한다.
